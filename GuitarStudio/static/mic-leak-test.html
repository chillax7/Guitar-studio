Input memory-leak bisect

Use Chrome's own task manager, not Activity Monitor. Press Shift+Esc (or ⋮ → More Tools → Task Manager) and find the row named “Input memory-leak bisect” — that is this tab, and its Memory footprint column is the number to watch. Activity Monitor only shows a pile of identically-named “Google Chrome Helper (Renderer)” processes with no indication of which tab each one belongs to, and if the leaking tab has already been discarded there may be no matching row at all — which makes “I saw no growth” impossible to distinguish from “I was watching the wrong process.”

Run one level at a time, leave it going 3–5 minutes, and note whether that row's memory climbs. Press Stop between levels. For a baseline, note the number before you start a level — the app itself sits around 1 GB, so what matters is the trend, not the absolute figure.

What the result tells us

  1. Level 1 climbs — the leak is in Chrome's capture stack itself. Nothing in the app is involved; the fix is a workaround plus a Chrome bug report.
  2. Level 2 climbs — it is createMediaStreamSource feeding an AudioContext, i.e. still Chrome, but tied to how we open the context.

  4. Level 4 climbs — an AudioWorklet in the live path is implicated, and that is ours to fix.
